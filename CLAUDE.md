# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

LAVA (Large-scale Automated Vulnerability Addition) automatically injects realistic, ground-truth
bugs into C programs, each paired with an input that triggers it. It's used to build corpora for
evaluating bug-finding tools. The project is a joint effort (MIT LL / NYU / Northeastern) and combines
a C++ Clang-based source-to-source rewriting toolchain with a Python orchestration package
(`pyroclastic`), PANDA (dynamic taint analysis via record/replay), and a PostgreSQL database that
stores candidate bugs mined from taint data.

## Build / test / run commands

Everything assumes Ubuntu 22.04 (or the `pandare/lava` Docker image) — this is not portable to
Windows execution; treat file edits as authoritative and expect actual builds/tests to run in CI or
a Linux/Docker environment.

- **Build the C++ tools (lavaTool, fbi, duasan, lavaDB, lavaODB) via CMake:**
  ```
  cmake -B"./tools/build" -H"./tools" -DCMAKE_INSTALL_PREFIX="/usr" -DCMAKE_BUILD_TYPE=Release
  cmake --build "./tools/build" --parallel "$(nproc)" --config Release
  ```
  Package as a `.deb` with `cpack -G DEB` from `tools/build`, then `apt-get install ./lava*.deb`.
- **Full local install (deps + build + install .deb):** `bash install.sh` (Ubuntu only, modifies the system).
- **Install the Python package:** `pip install .` from the repo root (needs
  `python/src/pyroclastic/data/lava.sql`, which is generated by the C++ build — build the tools first).
- **Initialize per-machine config:** `lava-init` (writes `~/.lava/host.json`; see
  `python/src/pyroclastic/utils/vars.py` for defaults). Requires `POSTGRES_USER` and
  `POSTGRES_PASSWORD` env vars to be set before running `lava`.
- **Run the Python test suite:** `pytest python` (pytest config/pythonpath in `pyproject.toml`; tests
  live in `python/tests/`). `test_explore.py` runs angr for ~7 minutes and needs a C compiler; set
  `LAVA_SKIP_ANGR_TESTS=1` to skip it (`test_explore_ptree.py` still runs, in under a second).
- **Generate new inputs for a target (concolic exploration):** `magmalyze -p <project>` (see the
  magmalyze section below and `python/src/pyroclastic/magmalyze/README.md`). `magmalyze-demo` shows
  KLEE random-path vs. DFS on two tiny targets.
- **Check an injected build stands alone:** `lava-verify target_injections/<project>/bugs/<n>/build<N>`
  rebuilds it from its tarball and replays the crashing inputs in its `manifest.json`.
- **Run the full LAVA pipeline against a target:** `lava -ak <project>` (or `python -m pyroclastic.lava
  -ak <project>`), where `<project>` matches a directory under `target_configs/`.
- **Run individual pipeline steps** (see `python/src/pyroclastic/lava.py::parse_lava_args` for all
  flags): `-q` add-queries, `-m` make, `-t` taint, `--sanitize`, `-i N` inject N trials, `-c` clean db,
  `-r` reset, `-k`/`--force` skip confirmation prompts.
- **CI reference:** `.github/workflows/parallel_tests.yml` shows the canonical sequence against the
  `toy` target (add-queries → make → taint → inject with specific `--bugtypes`) and is the best source
  of truth for exact invocation order/flags when something is ambiguous.

## Architecture: the pipeline

LAVA's steps run in a fixed order and each one depends on artifacts from the last. The pipeline is
driven by `python/src/pyroclastic/lava.py::main`, dispatching on CLI flags:

1. **`reset`** — deletes prior source/bugs/recordings for a project and re-creates the Postgres schema
   from `python/src/pyroclastic/data/lava.sql` (generated from `tools/lavaODB/src/lava.proto` via ODB).
2. **`add_queries`** (`python/src/pyroclastic/add_queries/add_queries.py`) — unpacks the target's
   tarball (from `target_bins/`, referenced by `target_configs/<project>/<project>.json`), configures
   and preprocesses it, then runs the Clang-based `lavaFnTool`/`fninstr.py`/`lavaTool -action=query`
   over every compilation unit to instrument it with taint queries (PRI/hypercall points) and attack
   points, recording them in the Postgres DB. `-arg_dataflow` is added when the project config sets
   `dataflow: true`. This step also does the *default* (non-static) build.
3. **`make`** (`lava.py::make_panda`) — rebuilds the instrumented source **statically** (PANDA guest VMs
   can't be assumed to have the target's shared libs) into `lava-install/`.
4. **`taint`** (`python/src/pyroclastic/taint/bug_mining.py::run_taint_pipeline`) — boots the statically
   built binary under PANDA (record/replay, using `pandare`), replays inputs, collects a pandalog
   (`queries-<project>.plog`/`.json`), and calls into `find_bug_injection.py` / `generate_bugs.py` to
   mine DUAs (dead/uninitialized/attacker-controlled bytes) and viable attack points from the taint
   data, writing candidate bugs into the `bug`/`dua`/`attackpoint`/`labelset` tables.
5. **`sanitize`** (optional) — runs the `duasan` Clang tool over `compile_commands.json` to filter DUAs
   the static analysis flags as unsafe to use.
6. **`inject`** (`python/src/pyroclastic/inject/inject.py`) — selects bug(s) from the DB (by id,
   random, balanced, or `--bugtypes` list) and re-runs `lavaTool -action=inject` to rewrite the source
   so the bug is actually present, then rebuilds. Each trial's output lands under
   `target_injections/<project>/bugs/<n>/`, and a git repo is initialized there with one branch per
   injected bug set.

Config for a target lives in two places that both must agree:
- `host.json` (per-machine paths: qemu binary, `output_dir`, `config_dir`, `tar_dir`, db suffix — see
  `host.json.example` and `LavaPaths`/`parse_vars` in `python/src/pyroclastic/utils/vars.py`).
- `target_configs/<project>/<project>.json` (per-target: `name`, `db`, `tarfile`, `make`/`install`
  commands, `command` template used to invoke it under PANDA, optional `dataflow`, optional
  `injfixupsscript`/`fixupsscript` shell scripts run after add-queries/inject to hand-fix things
  `lavaTool`'s source rewriting can't handle cleanly).

Adding a brand-new target is involved (pre-processing source, initializing variables, hand-fixing
Clang rewrite edge cases) — see `docs/how-to-lava.md` for the full manual process and known gotchas
(GNU attributes/extensions, `-O0 -g -gdwarf-2` requirements, function-pointer issues with
`-arg_dataflow`).

## Two halves of the codebase

- **`tools/` (C++, CMake, Clang LibTooling)** — the source-to-source transforms and analysis binaries:
  `lavaTool` (query/inject rewriting, `lavaFnTool`/`lavaInitTool` variants), `fbi` (`find_bug_inj`,
  parses pandalogs into bug candidates), `duasan` (DUA sanitizer), `lavaDB` (source-location/id
  bookkeeping shared across tools), `lavaODB` (ODB/protobuf-generated DB layer — `lava.proto` is the
  source of truth for the `Bug`/`Dua`/`Attackpoint` schema; `generated/lava.sql` is what actually gets
  applied to Postgres and must stay in sync with the Python side's `database_types.py`).
- **`python/src/pyroclastic/` ("pyroclastic")** — orchestrates the above: `lava.py` (CLI/pipeline
  driver), `add_queries/`, `inject/` (incl. `dataflow.py` for the `-arg_dataflow` helper injection),
  `taint/` (`bug_mining.py`, `find_bug_injection.py`, `generate_bugs.py` — the "2-phase" bug mining that
  must match the C++ `fbi` logic, per recent commit history), `utils/` (`vars.py` config/paths,
  `funcs.py` shared subprocess/build helpers, `database_types.py` SQLAlchemy models + `BugKind`/
  attack-point enums), `magmalyze/` (angr-based concolic exploration that generates new inputs, plus
  `llvm-cov` coverage; separate from the core injection pipeline, see its own section below).

Bug/attack-point type numbering is documented in `docs/db_enums.md` — treat it as authoritative and
keep `BugKind` in `database_types.py` in sync with `lava.proto`/`lava.hxx` if it changes. Current bug
kinds include the original `ptr_add`/`ret_buffer`/`rel_write`/`printf_leak` plus newer "chaff" bug
types (`malloc_off_by_one`, `chaff_stack_unused`, `chaff_stack_const`, `chaff_heap_const`,
`chaff_divzero`) from the Chaff Bugs paper work (`Chaff_bugs_paper.pdf`) — several of these are
commented out in CI (`.github/workflows/parallel_tests.yml`) because they aren't fully stable yet.

## `magmalyze/`: new inputs by concolic exploration

Why it exists: LAVA can only inject bugs along paths its taint inputs execute, which puts them next
to the fuzzers' "main path" (Bundt, Fasano et al., ASIA CCS '21, `fasano_ccs_paper.pdf`). magmalyze
generates inputs that reach other code, to be tainted and then held out of the fuzzer's seeds
(`docs/lava-upgrade-1.md` §11).

How it works (`angr_concolic_explore.py`):
- **Concolic, not symbolic.** Every byte of each seed is a symbolic `BVS`, preconstrained to the
  seed's bytes (angr's `SimStatePreconstrainer`), so a run follows the seed's real path. The other
  side of each branch comes back as an `unsat` successor (`save_unsat=True`). `SeedFlipper.flip()`
  drops the preconstraints, checks the branch is feasible, solves for a new concrete input, and
  preconstrains to it. A flip is a new input *and* a new run.
- **Search = KLEE random-path over an explicit process tree** (`ptree.py`, plain Python, no angr).
  `PTreeSearch` steps exactly ONE state per step, and a flip is just another child of a fork.
  `klee` walks from the root choosing children uniformly; `uniform` (random live state) and `dfs`
  share the same tree, as baselines.
- **Flip filters, all load-bearing** (each was a real bug when missing):
  only branches in the target's own code, not `/lib`/`/usr/lib` (`in_target`; libc flips OOM'd a
  run at 7 GB); only branches whose `history.jump_guard` depends on the input (loop counters and the
  stack-canary check otherwise fork runs that take the same path); not toward edges the seeds already
  cover (`seed_coverage_filter`); at most `max_flips_per_edge` per edge.
- **Memory:** finished states become `(input, stdout)` immediately and are dropped;
  `max_live_states` caps waiting runs. Each live state is a full angr state (~7 MB on labyrinth).
- **Output:** `InputSink` writes each new input the moment it's found (temp file + rename), one
  file per distinct content, plus `generated_inputs.jsonl`. A finished path's input equals its
  flip's, so records share files; `result.files` counts files, `result.inputs` counts records.
- **Long runs / SLURM:** SIGTERM stops cleanly; `--solver-timeout` (default 30 s per query) keeps
  one hard query from stalling a run; `--no-build`, `--output-dir`, `--seeds-dir` are for array jobs.
  The README's "Tune on a 1-hour run" section explains how to pick the settings.

Things to know before changing it:
- `explore()` is the LAVA-free core (a binary, argv, seed files); `perform_batch_concolic_exploration()`
  and `main()` wrap it for a LAVA project. Tests and the demo call `explore()` directly.
- There is no "window" mode any more (a random window of symbolic bytes); it was removed as a
  misreading of concolic execution. With `max_flips_per_edge=None, seed_coverage_filter=False`,
  concolic exploration covers a target's whole tree, which is what the strategy tests use.
- Targets for the tests are built from the tracked tarballs `target_bins/labyrinth*.tar.gz` (the
  unpacked `target_bins/*/` directories are gitignored). `labyrinth` is a balanced 256-path tree;
  `labyrinth_lopsided` puts one long fork-free path opposite 256 short ones, which is the only one
  that separates KLEE random-path from uniform selection. Test thresholds come from measured runs
  recorded in the test comments; re-measure before changing them.
- angr's own DFS shuffles a fork's children, so order metrics must not depend on child order (the
  tests use first-decision runs and shared prefix length, not rank correlation).

## `tools/lavaTool`: how source-to-source rewriting actually works

`lavaTool` is a single Clang LibTooling binary with two modes selected by `-action`
(`tools/lavaTool/include/lavaTool.h`, `enum action { LavaQueries, LavaInjectBugs, LavaInstrumentMain }`,
global `cl::opt<action> LavaAction`):
- `-action=query` → the **add_queries** step (instruments taint/PRI query points).
- `-action=inject` → the **inject** step (siphons DUAs + writes the actual bug payload).

`tools/lavaTool/include/MatchFinder.h` (`LavaMatchFinder`) registers all the AST matchers/handlers and
is the entry point for understanding what gets rewritten where:
- `stmt(hasParent(compoundStmt()))` → `PriQueryPointHandler` (every statement in a `{ ... }` block —
  this is where both PRI query hypercalls *and* DUA siphon/attack code get inserted).
- `functionDecl()` → `FuncDeclArgAdditionHandler` (per-function scaffolding + `-arg_dataflow` arg
  injection).
- other matchers (`MemoryAccessHandler`, `FunctionArgHandler`, `MallocOffByOneArgHandler`, and, only
  under `-arg_dataflow` during inject, `VarDeclArgAdditionHandler`/`FieldDeclArgAdditionHandler`/
  `CallExprArgAdditionHandler`/`FunctionPointerTypedefHandler`/`ReadDisclosureHandler`).
- `LavaMatchFinder::handleBeginSource` is where the macros the handlers below *call* actually get
  `#define`d and prepended to each translation unit during `-action=inject`. This is the single source
  of truth for what `lava_set`/`lava_get`/`lava_set_extra`/`lava_get_extra`/`lava_check_const_low_1..6`/
  `lava_check_const_high`/`lava_update_const_low`/`lava_update_const_high`/`lava_check_state` expand to,
  and for the backing storage: `lava_val[]`/`lava_extra[]`/`lava_state[]` (+`lava_chaff_pointer`) are
  defined **once**, non-`extern`, in whichever file is in the `main_files` set, and `extern`-declared in
  every other translation unit. A link error or a chaff bug that silently reads zeros is very often
  this file-role logic disagreeing with which file `lavaTool` thinks is "main" — check `MainFileList`/
  `main_files` first.

### Chaff bug injection walkthrough (stack/heap "look-real" bugs)

Chaff bugs (`CHAFF_STACK_UNUSED`, `CHAFF_STACK_CONST`, `CHAFF_HEAP_CONST`, `CHAFF_DIVZERO`) don't
corrupt a genuine attacker-reachable pointer the way `PTR_ADD`/`REL_WRITE` do — they synthesize a
plausible-looking corruption at a location LAVA controls. The moving pieces, in order:

1. **Stack scaffolding (every function, every action, unconditionally).**
   `FuncDeclArgAdditionHandler::handle` (`tools/lavaTool/include/FuncDeclArgAdditionHandler.h`) inserts
   three locals at the top of *every* function body with a `CompoundStmt`, before any whitelist check
   and before the `LavaAction == LavaQueries` early-return:
   ```c
   int lava_chaff_var_0 = 0;
   int lava_chaff_var_1 = 0;
   unsigned long lava_chaff_var_2 = (unsigned long) &lava_chaff_var_0;
   ```
   `lava_chaff_var_2` is the per-function stack anchor that `CHAFF_STACK_UNUSED`/`CHAFF_STACK_CONST`
   payloads compute byte offsets from. Because this runs in *both* the query pass and the inject pass,
   the two passes must keep generating it identically — if stack layout/offsets look wrong at runtime,
   diff the query-pass and inject-pass output for the same function first.
2. **Marking the chaff payload bytes.** During bug mining/DB population, the attacker-controlled
   "extra DUA" that will become the chaff payload is recorded via `mark_for_siphon_extra` (writes to
   `extra_siphons_at`/`extra_data_slots`, keyed by `ASTLoc`) — see `tools/lavaTool/include/lavaTool.h`.
3. **Over-constraining so the bug doesn't fire spuriously.** `mark_for_overconst_extra`
   (`lavaTool.h`) schedules extra checker/updater calls (`lava_check_const_low_*` /
   `lava_check_const_high` paired with `lava_update_const_low`/`_high`) at intermediate trace points
   between the DUA's siphon and the bug's attack point. Only if the attacker's bytes stay unperturbed
   across that whole window does `lava_check_state(slot)` (`lava_state[slot] == 3`, both low and high
   halves confirmed) end up true — this is what stops chaff bugs from triggering on every run. The
   window is bounded by the *next* re-visit of the same siphon source location, not by the attack
   point's trace index: attack points are deduplicated by location, so `bug->atp->trace_index` is
   only the first visit, which can come before a later loop iteration's DUA (see the comment at the
   top of `mark_for_overconst_extra`). The window can now extend past this iteration's attack point.
4. **Emitting the payload at the attack point.** `PriQueryPointHandler::AttackChaffBugs`
   (`tools/lavaTool/include/PriQueryPointHandler.h`) is called from `PriQueryPointHandler::handle` for
   every query-point statement, gated on `Test(bug) && lava_check_state(slot)`:
   - `CHAFF_DIVZERO` (and any chaff type under `-debug-inject`/`DebugInject`) → `InjectDivByZero`, a
     `__builtin_trap()` — use `-debug-inject` to confirm a chaff bug's *trigger condition* fires at all
     without worrying about whether the real memory-corruption payload works.
   - `CHAFF_STACK_UNUSED` → `memcpy`s 16 bytes onto the stack just below `&lava_chaff_var_2`, then
     writes through the dataflow arg pointer (`ARG_NAME`, i.e. `data_flow`).
   - `CHAFF_STACK_CONST` → writes the attacker-controlled `extra` value at
     `(char*)&lava_chaff_var_2 + bug->stackoff + sizeof(void*)`.
   - `CHAFF_HEAP_CONST` → `malloc`s a chunk and hand-corrupts glibc-malloc-style metadata offsets
     (`0x10`/`0x18`/`0x20`/`0x24`/`0x28`); the code has a `TODO: likely broken, only works on an old
     glibc` — treat failures here as a known gap, not necessarily a regression.

If a chaff bug isn't triggering, check in this order: (a) is `lava_chaff_var_2` scaffolding present and
identical between the query-pass and inject-pass source for that function, (b) does `main_files`
correctly own the one non-`extern` `lava_val`/`lava_extra`/`lava_state` definition, (c) did
`mark_for_overconst_extra`'s window get computed sanely (`tr_end < tr_start` fallback collapsing the
window to a single point is a red flag in `debug(INJECT)` logs), (d) re-run with `-debug-inject` to
isolate "trigger never fires" from "payload doesn't corrupt what we expect".

## Things to know before changing code

- The Python side and the C++ side must stay in lockstep: `BugKind`/attack-point enum values, the
  `NUM_BUGTYPES` constant in `inject.py`, and the Postgres schema (`lava.proto` → generated `lava.sql`)
  are all describing the same data and are not automatically kept in sync by any single source of
  truth — update all sides together.
- Compilation flags matter a lot for correctness, not just style: targets must build with
  `-O0 -g -gdwarf-2` (PANDA's PRI needs unoptimized code with DWARF2 info) and the `make` step
  specifically adds `-static` because PANDA guest VMs can't be assumed to have the target's shared
  libraries — don't "simplify" these away.
- `add_queries` and `make` are intentionally separate steps (not merged) — see the docstring on
  `make_panda` in `lava.py`; merging them has previously broken things in subtle, hard-to-diagnose ways.
- Never delete a database or on-disk project state without going through `reset`/`--force`/`-k` — the
  `LavaPaths.set_bugs_parent` / `reset_database` helpers assume a specific directory layout, and hand
  deletion can desync `bugs_top_dir` bookkeeping.
